# 付费形态调研 —— 给"小额付费开关"的决策弹药

> 产出日期：2026-09-26 ｜ 用途：项目负责人与小虾对付费形态拍板的决策依据
> 90 天验证目标：**≥10 笔真实小额付费**（真实出售证据）
> 本文档只做调研与方案对比，不含任何实现代码。所有联网数据抓取于 2026-09-25/26。

---

## 0. 先说结论（TL;DR）

**推荐：形态 B（打赏 + 低价单次解锁高级功能）先行，形态 A 退化为"高额度软墙"视拉新数据再叠加，形态 C（会员制）暂缓。**

三条理由，展开在正文：

1. **飞轮优先**：现在 13 台驻置设备、日识别个位数，数据飞轮的样本摄入本来就在饥饿线上。形态 B 对识别零限流，是唯一不伤飞轮的形态；任何按次收费的硬墙都是在饿死飞轮。
2. **10 笔的瓶颈是拉新不是形态**：日活个位数的量级下，三种形态靠自然流量都凑不齐 10 笔（测算见 §4）。既然形态不决定成败，就该选**上线最快、伤害最小**的——B 约 1.5~2.5 人日就能跑通全链路。
3. **竞品教训单向成立**：MeowTalk 把免费边界收太紧被差评围攻（"Not a free app"），萌小译高承诺（94.6% 准确率）低兑现被媒体定性"智商税"。我们体量小、无品牌，付不起这两类差评。

**代价句（要它 / 不要它）**：
- 要 **B**：代价是打赏/低价解锁的转化天花板低（0.1%~1%，见 §4.1），90 天 10 笔高度依赖小红书/抖音拉新配合，纯靠现有存量用户大概率凑不满；**不要 B**：代价是没有低成本试错路径，只能直接上重形态，一次押错 5~7 人日打水漂。
- 要 **A（软墙变体）**：代价是 5~6 人日工期 + 支付通道门槛（个人主体无营业执照，商户号难办，见 §6.2），且稍有不慎就把飞轮掐死；**不要 A**：代价是长期缺防滥用手段（短期有 10 次/分钟/IP 限流兜底，cloud_server.py:521-535）。
- 要 **C**：代价是 5~7 人日工期 + 月付决策门槛最重，当前用户量几乎必然凑不满 10 笔，还要处理"无自动续费能力"的会员有效期硬伤；**不要 C**：对飞轮和口碑无任何损失。

## 4. 三形态方案对比（每形态四笔账）

### 4.1 转化漏斗

| 形态 | 用户在哪个环节掏钱 | 转化率常识区间（依据） |
|---|---|---|
| A 免费次数制 | 免费用满 N 次 → 撞墙 → 当日无限解锁付费 | freemium 安装→付费中位 **1.7%**（RevenueCat 2024）；撞墙瞬间转化取决于"撞墙时需求强度"，工具类按 0.5%~2% 估 |
| B 单次解锁/打赏 | 识别成功、情绪被触发 → 结果页自愿掏钱（咖啡/解锁周报增强） | 纯打赏 **0.1%~0.5%**（行业常识区间，无权威基准）；"低价解锁具体功能"略高，按 0.5%~1% 估——**买的是确定的东西，不是情怀** |
| C 会员制 | 反复用到觉得离不开 → 月/年付承诺 | 承诺门槛最重。无试用机制时按安装→付费下限 **<1%** 估；RevenueCat 硬墙 10.7% 的前提是"先试用再扣款"，我们没有自动扣款能力，享受不到该口径 |

三形态里 B 的"单次解锁"变体（付费解锁一个具体的、看得到的东西）心理决策成本最低；C 的月付承诺对低频工具（一天听不了几次猫叫）最不成立。

### 4.2 对数据飞轮的影响（核心权衡，正面拆）

**现状基数**：13 台驻置设备、日识别个位数。按上限估：日识别 8~10 次，90 天 ≈ 720~900 次识别；其中置信度 ≥ 0.8 落飞轮样本的，按六成估（**假设，无后台实证，待 /stats 验证**）≈ 430~540 个样本。**在这个基数上，任何百分比的摄入损失都是绝对值上的重创。**

| 形态 | 飞轮伤害 | 机制拆解 |
|---|---|---|
| A 免费次数制 | **直接、成比例的伤害** | 墙挡的是 predict 调用本身（cloud_server.py:538），被挡的每一次都是零摄入。更隐蔽的二级伤害：**用户撞墙后的挫败直接降低回访率**，连免费额度内的识别也一起丢。若不豁免 source='station'，13 台驻置设备全部撞墙，等于亲手关掉飞轮主力（豁免方案见 §6.3） |
| B 打赏/单次解锁 | **零伤害** | 识别不限流，墙外自愿付费；高级功能（周报/统计增强）的解锁不减少识别次数。唯一注意点：解锁的"高级功能"不能反过来要求更多识别（不构成负反馈） |
| C 会员制 | 取决于锁什么 | 锁识别 = 同 A；只锁周报/统计增强 = 飞轮无害（PETKIT/Furbo/Petivity 的锁法）。但锁得越少，会员的付费理由越弱——C 的飞轮无害是以"付费吸引力弱"换来的 |

**这个矛盾没法两全，只能排序**：90 天验证清单同时要"10 笔付费"和（隐含的）模型变好。若必须牺牲一边，**数据纪律上应保飞轮**——因为 10 笔靠拉新可以补，飞轮样本错过的时间窗补不回来，且模型不准会反过来杀死一切付费（MeowTalk/萌小译的共同死因是"不准"，不是"收费"）。

### 4.3 实现成本（按 cloud_server.py 实读结构估算）

| 形态 | 需要动什么 | 工作量估算 |
|---|---|---|
| A 免费次数制 | ① 新表 `usage_quota(device_uid, date, count)` + `payments(order_id, device_uid, amount, status, created_at)`（照抄 cloud_server.py:77-136 建表模式）；② predict() 限流后插配额检查+station 豁免（~30 行，cloud_server.py:538 入口）；③ 支付：下单接口 + 微信 Native/JSAPI 支付 + 回调验签 + 订单状态机 + 到账解锁写库（**依赖商户号，个人主体难，见 §6.2**）；④ 前端：撞墙提示弹窗 + 付费按钮 + 状态刷新；⑤ 对账/退款处理 | 后端 3~4 人日 + 前端 1 人日 + 联调测试 1 人日 ≈ **5~6 人日**；若用"个人收款码+人工确认到账"省掉③，压到 **2~3 人日**，但无自动解锁 |
| B 打赏/单次解锁 | ① feedback-widget.js（268 行）加"请我喝咖啡"按钮 + 收款码弹窗 + 埋点（/api/event 已有，cloud_server.py:822 直接复用）；② 周报增强版加闸门：`/api/cats/<id>/report/weekly` 加已解锁 uid 校验（~20 行，cloud_server.py:1432）；③ 小表 `donations(device_uid, amount, note, created_at)` 人工登记到账（10 笔量级人工完全可行）+ /stats 页加一栏展示 | 前端 0.5~1 人日 + 后端闸门与登记 0.5 人日 + 测试 0.5 人日 ≈ **1.5~2.5 人日**，**不需要商户号** |
| C 会员制 | ① 新表 `members(device_uid, plan, paid_at, expire_at)`；② 支付同 A 的③（**且真正"订阅"需要自动续费，个人主体无 PAPAYA/委托代扣能力，只能做成"买 30 天有效期"，名不副实**）；③ 全站功能闸门（周报/统计/导出逐个挂检查）；④ 前端会员页 + 到期提示 + 续费流程 | 后端 3~4 人日 + 前端 1.5~2 人日 + 测试 1 人日 ≈ **5~7 人日** |

工作量假设：单人全栈、cloud_server.py 的既有模式（建表/限流/闸门）可直接照抄、无 UI 设计环节。若支付走商户号通道，另加个体户执照办理的**日历时间 1~2 周**（非人日，含审核）。

### 4.4 90 天凑 ≥10 笔的难度（诚实测算）

**共同前提**：当前 13 台设备、日活个位数。设 90 天累计独立用户 U（由拉新决定：纯存量 ≈ 20~40；有小红书/抖音内容引流 ≈ 200~2000，**纯假设区间，取决于运营投入**）。

| 形态 | 测算 | 凑 10 笔的前提 |
|---|---|---|
| A 次数制 | 转化 0.5%~2% × U。U=40（纯存量）→ 0.2~0.8 笔；U=1000 → 5~20 笔 | 需要 **U ≥ 500~2000** 的拉新量级，即 90 天内平均日新增 6~22 个独立用户。存量必死，拉新勉强可及 |
| B 打赏/解锁 | 打赏 0.1%~0.5%、单次解锁 0.5%~1% × U。U=40 → 最多 0.4 笔；U=1000 → 解锁 5~10 笔 | 需要 **U ≥ 1000~2000**，比 A 更吃流量；但单价低（1~3 元）冲动决策快，**爆款内容（猫叫翻译视频）带量时反而最可能爆单**——这是内容电商逻辑，不是订阅逻辑 |
| C 会员制 | 转化 <1% × U，且要求用户已建立信任。U=40 → ≈0；U=1000 → <10 笔且不稳 | 需要 **U ≥ 1000 且有 2~4 周使用留存的口碑用户**。90 天窗口内从个位数日活做到这个状态，是最难的一条路 |

**三种形态在存量用户上都凑不齐 10 笔，数学上不成立。10 笔的第一变量是拉新，第二变量才是形态。** 这就是"先用 B 把闸门和登记流程跑通、把力气花在拉新上"的测算依据。最现实的路径：一条爆款内容 + 结果页 1~3 元解锁 + 存量里发展 2~3 个铁杆（13 台设备的运营者是最可能的首批付费者，值得逐一私聊）。

## 5. 结论：推荐方案与理由

**推荐组合：B 先行（本周可上线）→ 30 天后看数据决定是否叠加 A 的软墙变体 → C 搁置。**

- **第 1~30 天：只上 B**。结果页"请我喝咖啡"（纯打赏，¥3/5/10）+ "¥1~3 解锁健康周报增强版"（锁的是 cloud_server.py:1432 已有的周报的增强视图，基础周报保持免费）。识别完全不限。验收口径：/stats 或 donations 表能数出真实到账笔数。**这一步同时验证"有人愿意为翻译结果掏钱"这个命题本身。**
- **第 31~60 天：若拉新起量（日新增 >20）且出现滥用（识别请求暴涨超飞轮处理能力）**，叠加 A 软墙变体：每日免费 20 次（远超正常使用量，只防脚本滥用）、source='station' 全豁免、超出引导付费而非直接拒绝。若无滥用，不叠加。
- **C 全程搁置**：无自动续费能力的"假会员"体验差，付费理由弱，工期最长，90 天窗口内性价比最低。若 B 的解锁笔数 >30，再考虑把"单次解锁"升级为"包月不限"（这本质是 A+C 的杂交，届时再议）。
